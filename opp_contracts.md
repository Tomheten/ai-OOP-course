# Контракты: type и interface

Документ стоит вне задач. Он объясняет понятие, на которое мы будем
опираться весь курс: контракт.

## Что такое контракт

В жизни контракт — это соглашение о том, что гарантируется.
Договор аренды: арендодатель гарантирует квартиру, арендатор — оплату.
Каждой стороне не нужно знать о другой всё — важно, что условия соблюдены.

В коде контракт — это описание формы объекта: какие поля и методы
гарантированно присутствуют. Код, работающий «через контракт», не
заботится, кто перед ним. Важно, что объект подходит по форме.

## Контракт — это то, что нужно полиморфизму

Полиморфизм держится на контракте. Клиенту не важно, какой конкретно
объект перед ним; важно, что объект подходит под контракт. Поэтому для
полиморфизма ключевым является само ПОНЯТИЕ контракта, а не конкретное
ключевое слово, которым он записан.

## Одно понятие — два ключевых слова

В большинстве ООП-языков (Java, C#, Go и др.) контракт выражается одним
инструментом — интерфейсом.

В TypeScript для контрактов предусмотрено ДВА ключевых слова:

    interface  и  type

Для описания контракта «какие поля и методы есть у объекта» они
ВЗАИМОЗАМЕНЯЕМЫ. Один и тот же контракт можно записать обоими способами:

    // контракт через interface
    interface NotificationSender {
      send(to: string, message: string): void;
    }

    // тот же контракт через type
    type NotificationSender = {
      send(to: string, message: string): void;
    };

Обе записи описывают одну и ту же форму. Благодаря структурной типизации
компилятору не важно, каким словом записан контракт, — он проверяет форму.

## Чем они различаются

Хотя для контракта объекта они взаимозаменяемы, возможности у них разные.

`type` умеет БОЛЬШЕ:
- объединения:  type TodoStatus = "active" | "completed";
- пересечения:  type A = B & C;
- кортежи, отображённые и условные типы.

Обрати внимание: статус задачи `TodoStatus` мы записали через `type`,
потому что `interface` НЕ умеет объединения. Это пример, где `type`
незаменим.

`interface` удобнее для контрактов классов:
- явное `implements`;
- расширение через `extends`;
- слияние объявлений (declaration merging).

## Что используем в курсе

- `type` — для форм данных и составных типов:
  Todo, TodoStatus, AppConfig, User.
- `interface` — для поведенческих контрактов под `implements`:
  NotificationSender, дальше Parser, NotificationRenderer.

Это СОГЛАШЕНИЕ курса, а не ограничение языка. Главное, что нужно
запомнить: и `type`, и `interface` описывают контракты. Для полиморфизма
важен сам контракт, а не то, каким словом он записан.

## Структурная типизация (важно)

TypeScript проверяет ФОРМУ, а не имя. Если объект имеет метод `send` с
нужной сигнатурой, он подходит под `NotificationSender` — даже если он
«не знал», что его так назовут.

Это значит:
- контракт — это именно форма, а не ярлык;
- одна и та же сущность может удовлетворять нескольким контрактам;
- полиморфизм работает именно благодаря структурной проверке.

## Связь с полиморфизмом

Полиморфизм, который мы встретили в Блоке 2, держится на контракте:

1. Есть контракт (`interface` или `type`) — что гарантируется.
2. Есть реализации (`class`) — как именно это делается.
3. Есть клиент — работает через контракт и не знает деталей.

Разные реализации используются одинаково — потому что все они подходят
под один контракт.
